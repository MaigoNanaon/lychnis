# 影子对决技术方案

## 1. 方案结论

建议采用 **“预录打谱事件回放”为主、可复现的随机影子为降级方案** 的混合架构。

- 主方案不是录屏，也不是录音，而是记录对手每次点击相对歌曲播放时间的毫秒时间戳，再在对决时按同一音频时钟回放。
- 预录事件体积小、同步稳定、能保留真实玩家的节奏习惯，最符合“影子对决”的产品含义。
- 随机打谱只适合作为没有兼容录像时的兜底，或者作为低成本机器人池；如果直接作为主方案，对手行为容易显得机械，玩家也难以相信自己是在和一个“影子”对决。
- 第一版可以全部使用内置本地数据，不依赖后端、账号系统或实时联网；后续再平滑升级为服务端影子池。

推荐优先级：

1. **V1：内置预录影子池 + 本地匹配动画**。
2. **V1.1：录制工具/调试入口，方便持续补充影子数据**。
3. **V1.2：Seed 随机影子作为兼容性降级**。
4. **V2：服务端上传、筛选和分发真实玩家影子**。

## 2. 需求理解与默认假设

本方案按以下体验理解需求：

1. 首页新增主按钮“开始对决”。
2. 点击后进入“匹配中”页面或全屏状态，持续约 3 秒。
3. 3 秒后展示“旗鼓相当的对手”，包括头像、昵称、水平标签、对决曲目和历史表现。
4. 玩家点击“开始对决”后进入横屏双屏游戏页。
5. 双屏上半区展示影子，下半区展示玩家；两边使用同一首歌、同一谱面版本、同一个播放时钟。
6. 影子按照预先录制的点击时间线自动打谱，玩家能够实时看到影子的点击点、连击和分数变化。
7. 歌曲结束后进入对决结算，展示双方分数、胜负、准确率和判定分布。

由于当前首页没有已选歌曲状态，V1 默认由匹配结果携带对决曲目。也就是说，影子记录与歌曲绑定，匹配到谁就使用该影子对应的歌曲进入对决。后续若要支持“先选歌再匹配”，只需要把 `songId` 作为匹配条件，不需要改变游戏核心。

“3 秒后”建议定义为 **最短展示 3 秒**，而不是依赖正好 3 秒完成数据加载：

- 本地版：固定 3 秒后完成匹配。
- 联网版：匹配数据和资源预加载可并行执行；即使提前完成，也至少展示 3 秒，避免页面闪烁。
- 超过超时时间仍失败时，切换到内置影子，而不是一直停留在匹配中。

## 3. 现有架构分析

当前项目是原生 HTML、CSS、JavaScript 单页应用，页面通过多个 `<section>` 和 `active` 类切换：

- `index.html`：曲库、播放、游戏、分享/结算等页面结构。
- `js/app.js`：维护当前歌曲、音频、游戏实例和页面跳转，负责事件绑定与结算。
- `js/game.js`：单轨节奏游戏引擎，负责谱面渲染、点击判定、计分和动画循环。
- `js/audio.js`：唯一音频播放时钟，通过 `currentTime` 和 `requestAnimationFrame` 驱动游戏。
- `js/songs.js`：歌曲、时长、BPM 和分段谱面数据。
- `css/styles.css`：所有页面和游戏样式。

当前游戏引擎的关键特征：

- `RhythmGame` 只构建一条轨道。
- 玩家点击调用 `tap()`，基于当前音频时间完成判定。
- `start()` 将游戏更新函数挂到 `AudioEngine.onTimeUpdate`，并从歌曲 0 毫秒开始播放。
- 分数、连击、Perfect/Great/Good/Miss 都保存在单个游戏实例中。
- 当前谱面包含 `tutorial`、`play`、`idle` 三类段落，主要表达“示范—模仿”玩法。

因此，影子对决不能简单地创建两个完整 `RhythmGame` 并让它们各播一次歌。两个音频实例会产生漂移，且 `AudioEngine.onTimeUpdate` 当前只有一个回调槽。正确做法是：

> 一个对决控制器、一个音频主时钟、两条独立轨道状态、两套计分器。

## 4. 两种影子来源对比

### 4.1 方案 A：随机打谱

随机打谱不应理解为在任意时间乱点，而应基于标准目标点生成一条“拟人化点击时间线”：

- 每个目标点按难度概率生成 Perfect、Great、Good 或 Miss。
- 命中的点增加一个正负时间偏差，例如 `-80ms ~ +80ms`。
- 少量生成额外误触。
- 使用固定 Seed，保证同一场对决重复播放时结果完全一致。
- 预先生成整场事件和最终分数，不在每一帧临时调用 `Math.random()`。

优点：

- 无需采集真实玩家数据。
- 可以无限生成对手。
- 可以按玩家能力动态控制胜率和压迫感。
- 实现和调试成本较低。

缺点：

- 节奏容易机械，缺少真实玩家连续偏快、偏慢、紧张失误等行为特征。
- 如果对手资料包装成真人，会产生体验上的欺骗感。
- 动态随机容易出现分数与“旗鼓相当”标签不一致。
- 无法形成“挑战某个真实历史表现”的核心卖点。

适用场景：

- 无可用预录影子时的降级。
- 新歌曲刚上线、影子池为空时的冷启动。
- 明确标识为“训练机器人”的独立模式。

### 4.2 方案 B：提前录制打谱节奏

录制内容是结构化事件，不是媒体文件。一次录制至少包含：

- 歌曲 ID 和谱面版本。
- 每次点击相对音频开始的时间戳。
- 可选的原始判定、连击和最终结果，用于校验。
- 对手展示资料和能力标签。

优点：

- 点击间隔、系统性偏差和偶发失误都来自真实操作，更像一个人。
- 同一影子的回放和最终成绩是确定的，便于测试和复盘。
- 数据体积非常小，一首歌通常只是几十到几百个数字。
- 不需要第二路音频，不增加明显的网络与解码成本。
- 将来可以自然升级为“挑战好友影子”“挑战昨日的自己”。

缺点：

- 每首歌、每个谱面版本都需要兼容的录制数据。
- 谱面发生变化后，旧影子必须失效或迁移。
- 需要录制入口、校验规则和影子池管理。

适用场景：

- 正式的“影子对决”。
- 固定剧情对手、好友历史成绩、高手挑战。
- 需要稳定复现胜负和演出效果的 Demo。

### 4.3 最终选择

选择 **方案 B 作为主方案**，方案 A 作为兜底。

为了控制第一版成本，V1 不需要做完整的用户录制产品功能，可以先通过开发模式录制 6～10 份内置影子：

- 每首可对决歌曲准备至少 2 个水平档位。
- 对手显示为预设虚拟角色，避免误导为实时真人。
- 匹配时优先选择与玩家能力接近的预录记录。
- 没有历史能力数据时使用中等水平影子。

## 5. 总体架构

建议新增以下逻辑边界，具体可以根据现有原生项目风格拆成独立文件：

| 模块 | 责任 | 是否持有状态 |
|---|---|---|
| `DuelMatchController` | 匹配倒计时、候选筛选、资源预加载、取消和降级 | 是 |
| `ShadowRepository` | 读取内置或远端影子，校验歌曲和谱面版本 | 否 |
| `ShadowGenerator` | 根据 Seed 生成降级影子事件 | 否 |
| `DuelGame` | 使用一个音频时钟驱动双轨、双方计分和结算 | 是 |
| `LaneRenderer` | 渲染单条轨道、扫描线、点击点和判定反馈 | 是 |
| `JudgeEngine` | 目标点匹配、判定窗口、分数与连击计算 | 是 |
| `ShadowPlayback` | 按事件游标消费影子点击时间线 | 是 |
| `DuelResult` | 汇总双方结果并计算胜负 | 否 |

依赖方向：

```text
app.js
  ├─ DuelMatchController
  │    ├─ ShadowRepository
  │    └─ ShadowGenerator（降级）
  └─ DuelGame
       ├─ AudioEngine（唯一主时钟）
       ├─ LaneRenderer × 2
       ├─ JudgeEngine × 2
       └─ ShadowPlayback
```

核心约束：

1. **音频时间是唯一真相来源**，不使用累计 `setTimeout` 驱动影子。
2. 玩家和影子的判定必须调用同一套规则，禁止影子直接播放预存分数。
3. 影子点击事件必须经过 `JudgeEngine` 重算，录制结果只用于数据校验。
4. 双轨只是显示和状态分离，不复制音频播放。
5. 所有随机结果在开局前固定，保证对局可复现。

## 6. 页面与交互流程

### 6.1 首页

在当前曲库首页顶部标题区域下增加主入口：

- 主按钮：`开始对决`
- 辅助说明：`匹配一位旗鼓相当的节奏影子`
- 原有曲库和单人玩法保留，避免本次改造破坏已有路径。

点击后：

1. 停止播放页可能残留的音频。
2. 初始化新的 `matchSessionId`。
3. 进入匹配页。
4. 同时启动 3 秒最短展示计时、影子筛选和音频预加载。

### 6.2 匹配中

匹配页状态包括：

- 旋转或波纹动画。
- 文案“正在寻找旗鼓相当的对手…” 。
- 当前玩家能力标签，例如“节奏新星 / 稳定发挥”。
- “取消匹配”按钮。

匹配时长规则：

```text
matchReadyAt = max(matchStartedAt + 3000ms, dataReadyAt)
```

取消匹配后必须：

- 清除计时器。
- 使当前 `matchSessionId` 失效。
- 忽略迟到的异步结果。
- 回到首页。

### 6.3 匹配成功

展示对手卡片：

- 头像、昵称。
- “旗鼓相当”标签。
- 对决曲目、难度、预计时长。
- 对手历史准确率或能力值。
- 影子类型标识，例如“历史影像”或“训练影子”。
- 主按钮“开始对决”。
- 次按钮“换一个”，可选，V1 可以不做。

这里不建议自动进入游戏。保留“开始对决”确认动作可以让玩家看清曲目、完成横屏切换，并满足浏览器对音频播放必须由用户手势触发的限制。

### 6.4 对决游戏页

沿用之前开房间对决的双屏思路，建议横屏上下分屏：

- 上半屏：影子轨道，头像、昵称、实时分数和连击。
- 中间：歌曲进度、当前领先方和分差。
- 下半屏：玩家轨道，实时分数、连击和点击区域。
- 左上：退出。
- 右上：帮助。

上下分屏比左右分屏更适合当前横向轨道，因为每条轨道仍然拥有足够宽度表达时间轴；左右分屏会显著压缩轨道长度，降低点击位置可读性。

点击区域只绑定玩家半屏。影子半屏设置为非交互，避免事件冒泡导致玩家误触。

建议取消单人模式里的“先看教程段，再在下一段模仿”的文案包装，对决模式统一表达为双方打同一套目标节奏。底层可继续复用现有 `play` 段目标；如果仍需保留 `tutorial` 段，则双方只观看、不计分，进入 `play` 段后双方同时计分。

### 6.5 对决结算

结算页至少展示：

- 胜利、失败或平局。
- 玩家与影子的总分。
- 分差。
- 双方准确率和最大连击。
- Perfect/Great/Good/Miss 对比。
- 再来一局、返回首页。

V1 建议判胜规则仅比较 `score`：

1. 总分高者获胜。
2. 总分相同则准确率高者获胜。
3. 仍相同则最大连击高者获胜。
4. 三项都相同则平局。

## 7. 状态机设计

页面级状态建议显式定义为：

```text
HOME
  → MATCHING
  → OPPONENT_READY
  → DUEL_PREPARING
  → DUEL_PLAYING
  → DUEL_FINISHED

MATCHING → HOME             取消或不可恢复错误
OPPONENT_READY → MATCHING   更换对手
DUEL_PREPARING → HOME       资源加载失败
DUEL_PLAYING → DUEL_FINISHED 正常结束或主动中止
DUEL_FINISHED → OPPONENT_READY 再来一局
```

建议在 `app.js` 的全局状态中增加：

| 字段 | 说明 |
|---|---|
| `mode` | `solo` 或 `shadow-duel`，避免影响现有单人路径 |
| `duelPhase` | 当前对决状态机阶段 |
| `matchSessionId` | 防止取消后旧异步结果污染新状态 |
| `matchedShadow` | 当前匹配到的影子元数据与事件 |
| `duelGame` | 当前双轨游戏实例 |
| `duelResult` | 双方结果和胜负 |
| `playerSkillRating` | 本地能力估值，可从历史成绩计算 |

不要只依赖 DOM 是否带 `active` 类推断业务状态，否则匹配取消、音频加载失败和重复点击很容易产生竞态。

## 8. 数据模型

### 8.1 影子记录

建议的数据结构如下，字段名可在实施时按项目风格调整：

```json
{
  "id": "shadow_qingtian_001",
  "source": "recorded",
  "profile": {
    "name": "节拍小岚",
    "avatar": "assets/avatars/shadow-lan.png",
    "title": "稳定型",
    "rating": 1280
  },
  "songId": "qingtian",
  "chartVersion": "qingtian-v1",
  "recordingOffsetMs": 0,
  "events": [
    { "time": 5120, "type": "tap" },
    { "time": 5612, "type": "tap" },
    { "time": 7638, "type": "tap" }
  ],
  "summary": {
    "score": 12680,
    "accuracy": 91.4,
    "maxCombo": 27
  }
}
```

字段说明：

- `time` 必须是相对同一歌曲音频起点的毫秒数。
- `chartVersion` 必须参与兼容性判断，不能只检查 `songId`。
- `recordingOffsetMs` 用于修正录制设备或历史版本的统一偏移，默认 0。
- `summary` 不参与实际判分，只用于匹配展示和数据完整性校验。
- V1 只支持 `tap`，未来增加长按时再扩展 `down`、`up` 或 `duration`。

### 8.2 谱面版本

当前歌曲数据没有显式谱面版本。影子上线前必须给每首歌曲增加稳定版本号，或者由构建流程生成谱面哈希。

推荐 V1 使用人工版本号：

```text
chartVersion = `${songId}-v1`
```

以下变化必须提升版本号：

- 目标点击时间变化。
- 分段起止时间变化。
- 判定目标的映射规则变化。
- 音频文件被替换、裁剪或增加前置静音。

只修改封面、歌名或视觉样式不需要提升谱面版本。

### 8.3 匹配结果

匹配结果应包含本局不可变配置：

```json
{
  "matchId": "local-1722300000000",
  "songId": "qingtian",
  "chartVersion": "qingtian-v1",
  "shadowId": "shadow_qingtian_001",
  "source": "recorded",
  "seed": null,
  "createdAt": 1722300000000
}
```

开始游戏后不要重新随机选对手，也不要重新生成事件。

## 9. 影子录制方案

### 9.1 记录方式

录制工具复用正常游戏输入链路：

1. 开始播放时清空事件数组。
2. 每次玩家点击时读取 `AudioEngine.getCurrentTime()`。
3. 写入 `{ time, type: 'tap' }`。
4. 结束后使用当前判定引擎重新计算结果。
5. 导出 JSON，经校验后放入内置影子池。

禁止使用 `Date.now()` 或“距离上次点击的间隔”作为最终存储格式。绝对的歌曲相对时间更容易校验、裁剪、回放和迁移。

### 9.2 录制校验

一份影子数据进入影子池前需要通过：

- `songId` 存在。
- `chartVersion` 完全一致。
- 事件按时间升序排列。
- 所有时间位于 `0 ~ duration`。
- 不存在异常高频输入，例如 30ms 内大量重复事件。
- 使用当前判定引擎重算后的结果与 `summary` 在允许误差内一致。
- 能力值落在对手配置标注的区间。

### 9.3 回放方式

`ShadowPlayback` 保存一个事件游标 `nextEventIndex`。每次音频时钟更新时：

```text
effectiveTime = audioCurrentTime + shadow.recordingOffsetMs

while nextEvent.time <= effectiveTime:
  将该点击送入影子 JudgeEngine
  在影子轨道绘制点击点和判定动画
  nextEventIndex += 1
```

为防止低帧率设备漏事件，必须使用 `while` 消费当前帧之前的所有事件，不能每帧最多处理一个。

影子事件实际判定时要使用事件自身的 `time`，不能使用当前帧时间。否则页面卡顿会把本来准确的影子点击判成 Miss。

## 10. 随机影子降级方案

随机影子应在开局前一次性生成完整事件数组，并与普通预录影子走同一回放链路。

### 10.1 输入

- 标准目标点列表。
- 目标能力值或难度档位。
- 固定 Seed。
- 玩家近期能力值。

### 10.2 生成策略

建议为每个虚拟对手定义风格参数：

| 参数 | 含义 |
|---|---|
| `perfectRate` | Perfect 概率 |
| `greatRate` | Great 概率 |
| `goodRate` | Good 概率 |
| `missRate` | 漏击概率 |
| `biasMs` | 整体偏快或偏慢 |
| `jitterMs` | 单点随机抖动范围 |
| `mistakeBurst` | 连续失误倾向 |
| `extraTapRate` | 误触概率 |

为了更像真人，不能让每个点完全独立随机。建议加入：

- 一局固定的系统性偏差，例如整体快 18ms。
- 缓慢变化的漂移，而不是每个点大幅跳变。
- 少量连续失误段，而不是均匀分布的 Miss。
- 结尾紧张或追分时的小幅能力变化。

### 10.3 可复现性

Seed 建议由以下内容生成：

```text
seed = hash(matchId + shadowProfileId + songId + chartVersion)
```

生成后把事件数组保存在本局状态中。重试同一对手时可以选择：

- 复用 Seed：真正挑战同一个影子，推荐默认行为。
- 生成新 Seed：相当于重新匹配，不应仍显示同一场回放。

## 11. 匹配策略

### 11.1 玩家能力估值

V1 可以直接利用本地排行榜成绩计算简化能力值：

```text
skillRating = 最近最多 5 局标准化成绩的加权平均
```

没有历史成绩时使用默认中位值，并显示“初次匹配”。

标准化时优先使用准确率，其次使用最大连击，避免不同歌曲音符数量不同导致裸分不可比。

### 11.2 候选筛选

筛选顺序：

1. `songId` 和 `chartVersion` 兼容。
2. 影子能力值与玩家能力差在首选区间内。
3. 排除最近刚匹配过的影子，增加新鲜感。
4. 多个候选时随机选择，但记录到 `matchId` 后不再变化。
5. 没有候选时生成随机影子。

建议能力差区间：

- 首选：玩家能力值的 `±5%`。
- 次选：`±10%`。
- 仍无候选：选择最近的预录影子。
- 完全无兼容数据：使用 Seed 随机影子。

“旗鼓相当”应由可解释的能力区间得出，而不是只显示固定文案。

## 12. 双轨同步与判定

### 12.1 单一主时钟

所有逻辑都读取同一个 `AudioEngine.getCurrentTime()`：

- 扫描线位置。
- 玩家点击判定。
- 影子事件回放。
- 双方 Miss 补判。
- 歌曲进度和结束时机。

不为影子创建音频，不为每个事件创建独立长时 `setTimeout`。

### 12.2 输入与事件时间

- 玩家点击：在事件发生时读取音频时间，立即判定。
- 影子点击：回放循环发现事件到期后，用记录中的事件时间判定。
- 渲染动画可以晚一帧出现，但计分时间不能被该帧延迟污染。

### 12.3 判定器复用

建议把当前 `RhythmGame._judge()`、Miss 补判和准确率计算拆成独立 `JudgeEngine`，双方各持有一个实例。

若第一版希望减少重构，也可以让 `DuelGame` 内部维护两套与现有一致的计分字段，但必须确保双方调用同一判定函数，不能复制两份容易漂移的逻辑。

### 12.4 目标点映射

当前谱面是分段结构。对决模式需要明确“哪些点参与双方计分”：

- `play` 段：双方计分。
- `tutorial` 段：默认仅展示，不计分。
- `idle` 段：不计分。

如果希望整首歌从头到尾都在对决，需要为所有可计分段提供明确目标点，而不是依赖“教程段复制到下一段”的隐式关系。建议后续将“目标节奏”和“单人玩法分段”解耦：

- 歌曲层保存统一目标点。
- 单人模式决定哪些目标点用于示范、哪些用于玩家模仿。
- 对决模式直接让双方打统一目标点。

V1 可以先继续使用现有 `play` 段，降低改动范围。

## 13. 资源加载与异常处理

### 13.1 匹配阶段预加载

3 秒匹配动画期间并行执行：

- 读取影子 JSON。
- 查找歌曲与谱面。
- 预加载歌曲音频。
- 预加载对手头像。
- 校验影子兼容性。

匹配成功页只有在必要资源可用后才允许点击“开始对决”。

### 13.2 降级规则

| 异常 | 处理 |
|---|---|
| 预录影子不存在 | 使用 Seed 随机影子 |
| 谱面版本不兼容 | 排除该影子，不强行回放 |
| 头像失败 | 使用默认头像 |
| 音频预加载失败 | 提示重试或返回首页 |
| 匹配异步超时 | 使用内置影子完成匹配 |
| 页面切后台 | 暂停音频与对决，回前台后倒计时恢复 |
| 对决中主动退出 | 标记中止，不计入玩家能力值 |
| 低帧率漏过多帧 | 批量消费影子事件，按事件原始时间判定 |

### 13.3 生命周期清理

离开匹配或对决页面时必须清理：

- 匹配计时器。
- `requestAnimationFrame`。
- 音频回调。
- 页面可见性监听。
- 轨道 DOM 和粒子动画。
- 当前影子事件游标。

重复进入对决时不得叠加事件监听器。

## 14. 文件改动规划

本轮只输出方案，不修改代码。后续实施建议按以下范围进行：

| 文件 | 预计改动 | 说明 |
|---|---:|---|
| `index.html` | 中 | 增加首页入口、匹配页、对手确认页和双轨对决结构 |
| `css/styles.css` | 大 | 增加匹配动画、对手卡片、上下双屏和对决结算样式 |
| `js/app.js` | 大 | 增加对决状态机、匹配流程、资源预加载、事件绑定和结算 |
| `js/game.js` | 大 | 从单轨引擎演进为可复用判定器和双轨对决控制器 |
| `js/songs.js` | 小到中 | 增加谱面版本，必要时补充对决目标点 |
| `js/audio.js` | 小 | 保持单时钟，可能补充暂停恢复和多订阅能力 |
| `js/shadows.js` | 新增 | 内置影子资料与预录事件池 |
| `js/shadow-generator.js` | 新增 | Seed 随机影子降级生成器 |
| `js/duel.js` | 新增 | 匹配控制、双轨游戏和影子回放逻辑 |

推荐不要继续把所有逻辑堆进 `app.js`。对决引入后，状态和生命周期复杂度明显提高，至少应将影子数据、匹配和双轨游戏拆开。

## 15. 实施分期

### 阶段一：可玩的本地影子对决

- 首页“开始对决”。
- 固定 3 秒匹配动画。
- 2～3 个内置预录影子。
- 匹配成功确认页。
- 单音频时钟驱动上下双轨。
- 双方实时分数、连击与胜负结算。
- 无后端、无上传。

### 阶段二：内容与稳定性

- 为每首歌补充多个能力档位影子。
- 加入 Seed 随机影子降级。
- 增加录制与 JSON 导出工具。
- 增加谱面版本校验和数据校验脚本。
- 增加切后台暂停、低帧率和异常恢复。

### 阶段三：真实玩家影子池

- 登录用户上传影子。
- 服务端按歌曲、谱面版本、能力和质量筛选。
- 好友影子、昨日自己的影子、榜首影子。
- 防作弊、隐私授权、数据过期和版本迁移。

## 16. 验收标准

### 16.1 流程

- 首页点击“开始对决”后立即显示匹配中。
- 匹配状态至少持续 3 秒，期间可取消。
- 3 秒后展示一名兼容且能力接近的对手。
- 点击“开始对决”后能通过用户手势正常启动音频。
- 对决页为上下双屏，两条轨道同步于同一首歌。
- 歌曲结束后展示双方结果和明确胜负。

### 16.2 同步

- 影子点击使用记录时间判定，不受渲染帧延迟影响。
- 同一影子重复游玩时事件、分数和判定结果一致。
- 双轨扫描线在整局内无肉眼可见漂移。
- 页面发生短时卡顿后，影子事件不会漏播或重复播放。

### 16.3 数据

- 影子只会匹配相同 `songId` 和 `chartVersion` 的谱面。
- 不兼容影子自动排除。
- 随机降级影子在相同 Seed 下结果一致。
- 主动退出或资源失败不会写入玩家能力记录。

### 16.4 兼容性

- 原有曲库、播放、单人游戏和排行榜入口保持可用。
- 竖屏设备仍显示横屏提示。
- 音频加载失败时不会进入空白游戏页。
- 快速重复点击入口不会创建多个并行匹配任务。

## 17. 待产品确认项

以下问题不阻塞 V1 按默认方案实施，但在视觉和文案定稿前需要确认：

1. 对决曲目是“匹配结果指定”，还是“玩家先选歌再匹配”。本方案默认前者。
2. 对手应包装为虚拟角色，还是明确展示为某位真实玩家的历史影子。V1 建议虚拟角色。
3. `tutorial` 段在对决中是双方观看，还是也参与计分。本方案默认不计分。
4. 中止对决后是否展示当前比分。本方案建议展示“本局已中止”，但不计入能力值。
5. 再来一局是复用同一影子，还是重新匹配。本方案建议默认复用，另提供“换个对手”。

## 18. 最终建议

如果只在两种方案中二选一，选择 **提前录制打谱节奏**。

它的实现成本并不高：真正需要保存的只是点击时间戳数组，却能获得比随机打谱明显更真实、更稳定、更有产品辨识度的体验。随机打谱仍然值得保留，但应被定位为影子池为空时的技术降级，而不是“影子对决”的核心内容。

第一版最稳妥的落地方式是：**内置预录影子 + 本地 3 秒匹配 + 单时钟双轨回放 + Seed 随机兜底**。
